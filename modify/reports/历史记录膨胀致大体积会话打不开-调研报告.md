## 四、机制链路与根因（v2 修正）

### 4.1 v1 的错误结论

v1 认为「白屏 = `chatStore.ts:2318-2322` 在 `historyComplete=false` 时把 `messages` 置空」。**该判断不成立**：置空的是供派生状态（goal/todos/usage）使用的局部变量 `messages`；时间线渲染用的是 `uiMessages`（`chatStore.ts:2323`），它由**完整** `response.messages` 构建，应用分支（3814/3914）**未受 `historyComplete` 门控**。

### 4.2 真实根因：首个 `mode=full` 请求 120s 超时

`fetchAndMapSessionHistory`（`chatStore.ts:2313`）第 **2318 行 `await sessionsApi.getFullHistory()`**——整个加载是**阻塞式**的：在它 resolve 之前，不进任何 apply 分支，时间线始终是初始 `[]`。

诊断日志中的决定性证据：

```
summary: GET /api/sessions/4e1f6c0c-…/messages?mode=full failed: Request timed out after 120s
summary: GET /api/sessions/db39b34d-…/messages?mode=full failed: Request timed out after 120s
```

| 证据 | 数值 |
|---|---|
| `timed out after 120s` 次数 | **12** |
| 涉及会话 | `4e1f6c0c`（**仅 13.6 MB**）×2、`db39b34d`（114 MB）×2 |
| 客户端默认单请求超时 | `DEFAULT_REQUEST_TIMEOUT_MS = 120_000`（`desktop/src/api/client.ts:18`） |
| 服务端 `messages` 请求最大耗时 | 实测 27.6 s / 26.5 s / 15.0 s（服务端日志） |

**关键反例**：`4e1f6c0c` 只有 13.6 MB 也超时 ⇒ **瓶颈不只是字节量**。合理解释（已确认的代码事实）：`getSessionHistoryPage` 在 `projectContext !== false` 时会走 `readHistoryContexts`，该路径用 **context lane（capacity=1）** 做**全文件索引重建**；lane 串行 → 与其他会话/多个标签页并发时排队，叠加远端 gzip 的同步 `gzipSync` 阻塞事件循环，13.6 MB 也可能冲破 120 s。

### 4.3 字节量仍会放大该问题（次要但确定）

`src/server/services/boundedSessionHistory.ts`：

| 常量 | 值 | 含义 |
|---|---|---|
| `HISTORY_FULL_BYTES` | 32 MB | full 模式输出上限 |
| `HISTORY_FULL_SCAN_BYTES` | 64 MB | full 模式 I/O 扫描上限 |
| `HISTORY_PAGE_BYTES` | 256 KB | page 模式输出上限 |
| `HISTORY_SEMANTIC_RECORD_BYTES` | 8 MB | 整条透传门槛 |
| 并发池 | page 2/8、context **1**/4、recovery 1/2、metadata 2/128 | 饱和抛 429 `HISTORY_BUSY` |

两条放大机制：

1. **超预算记录独占一页**（249-258 行）：`if ((outputBytes+entryBytes > byteBudget || …) && entries.length) break`——空页时超预算记录照收（注释 "A record above the ordinary page budget owns its page"）。3.9 MB 单条 <8 MB 门槛，不被 skip，于是**独占一页**。实测翻页 **152 页未结束**（每页 ~1.5 s，累计扫描 178.5 MB），推算 200+ 页。
2. **主历史路径不做 preview**：`displayPreview()`（`boundedSessionHistory.ts:96`）已实现（48 KB/2048 节点），但**全仓唯一调用点**是 `sessionService.ts:4166`（子代理查询）；`entryToMessage`（`sessionService.ts:1913`）对 `toolUseResult` **原样透传**。

### 4.4 远端 H5 的额外放大

- 非 loopback 走 gzip（`responseCompression.ts`，仅远端默认开启）：32.6 MB → 8 MB（5×）；
- 但实现是 `await response.arrayBuffer()` + **同步 `gzipSync`**（:63、85）——整包缓冲 + 阻塞事件循环；每页另有 3 个 4 KB 锚点 sha256 + 边界指纹比对。**页数越多，CPU 开销线性放大，抵消带宽收益。**
- 前端 `MAX_JSON_RESPONSE_BYTES = 530 MB`（`client.ts:102`）是大历史下的硬上限风险；活跃标签页的 114 MB 历史**不受** `CHAT_HISTORY_CACHE_BYTES=16MB` 驱逐保护。

## 七、可行性实施方案（近乎完备）

> 分层设计，**互相独立可单独落地**；推荐顺序 A → B → C → D → E → F（A/B 无数据变更、风险最低，先拿收益）。

### A. 读取层：主历史路径套用 preview（立即缓解，不动存量数据）

**目标**：让**未迁移**的存量大会话立刻可打开。

- 在 `sessionService.entryToMessage`（:1913）/ `entriesToMessages` 的**展示投影**上，对 `toolUseResult` 套用与 `displayPreview` 同款的**有界预览**（大字符串 → 前 N KB + 省略标记）。
- **恢复/语义路径不裁**：`sessionHistoryRecovery.ts:174`（workspace 证据）、`teamService`、`workflowService` 继续拿原始记录。
- ⚠️ **严格遵守 C9**：展示裁剪**不得**置 `bodyTruncated`，或把 `contentTruncated` 与 `historyComplete` 解耦（否则历史被判「不完整」→ recovery 循环 + 横幅误显）。
- 预期：`mode=full` 输出 33.2 MB → **<2 MB**；单页可容 ~200 条。

**风险**：低。改动集中在服务端投影；需覆盖「有/无 `originalFile`」两种存量形态。

### B. 首屏解耦：不再阻塞式全量加载（消除 120 s 白屏）

**目标**：白屏的直接原因。

1. **渐进渲染**：`chatStore.fetchAndMapSessionHistory` 改为「首个响应到达即 apply 并渲染」，剩余页在后台继续 prepend（`loadOlderHistoryPage` 的 prepend 机制**已存在**，`chatStore.ts:2852`）。不要把加载结果攒到最后一次 apply。
2. **首屏绕开 context lane**：初始历史请求带 `projectContext:false`（C10），避开 context lane（cap=1）的全文件索引重建；索引改为**后台预热**或按需。
3. **超时兜底**：`getFullHistory` 显式设上限；失败时**保留已渲染内容**并提示（现有 catch 只置 `historyStatus:'error'`，不清空，可复用）。

**风险**：中。改的是核心加载路径，需覆盖：并发写入（`sourceVersion` 不匹配会非重试抛错，`api/sessions.ts:466`）、429 `HISTORY_BUSY`、切会话代际（`historyLifecycleGenerations`）。

### C. 写入层：持久化边界做有界裁剪 + 引用（根治新增）

**落点**：`sessionStorage.ts` 的 `cleanMessagesForLogging`（:4716-4727）/ `transformMessagesForExternalTranscript`（:4662-4714）——**落盘唯一收口**，在此做 transform 不动内存态（当前会话 TUI 仍拿完整内容）。

对超阈值（建议 **16 KB**，对齐 `displayPreview` 单字符串上限；小文件编辑**零回归**）的 `originalFile`：

```ts
originalFile          = 前 16 KB + 省略标记        // 保持 string，满足 C1/C2
originalFileTruncated  = true                     // 新增可选键
originalFileBytes      = <原始字节数>              // 新增可选键
originalFileRef        = { backupFileName?, sessionId?, filePath }  // 新增可选键：指向 file-history
```

- 同步把 `originalFileTruncated` / `originalFileBytes` / `originalFileRef` 加入 `FileEditTool/types.ts` 与 `FileWriteTool` 的 outputSchema（**可选**字段，保证 safeParse 通过）。
- 键**加在 `toolUseResult` 内部** → 满足 C4，不影响解析不变量。
- `toolUseResult` 对象**保留**（满足 C3），只是内容变小。
- 对**未被 file-history 追踪**的文件（本会话 340 条快照中 20 条 `trackedFileBackups` 为空，多为 workspace 外路径）→ 只做有界预览，`originalFileRef` 省略。

**预期**：本会话 114.3 MB → **约 38 MB**；新会话不再膨胀。

### D. 按需取回原文（补齐 C 的保真度）

**新增端点**：`GET /api/sessions/:id/file-history/content?path=<filePath>`（或 `?messageId=&path=`）。

- 服务端：`getSessionFileHistorySnapshots(sessionId)`（`sessionService.ts:5036`）→ 定位 `trackedFileBackups[path].backupFileName` → `readBackupFileSafely(backupFileName, sessionId)`（C7）→ 返回内容。
- 输出加界（建议 ≤2 MB，超限返回明确错误码，沿用既有 413 语义）。
- **安全**：复用 `readBackupFileSafely` 全套校验；远端（H5）须过 `remoteBrowserPolicy` 同级鉴权，与现有 admin 路由一致。
- **消费方**：CLI TUI diff 预览在检测到 `originalFileTruncated` 时按需拉取；桌面端零改动（C6）。
- 备选（更省事）：扩展既有 `turn-checkpoints/diff` 返回 `before` 字段，避免新端点——但语义耦合，推荐独立端点。

### E. file-history 冗余治理（独立膨胀，550 MB）

**成因（已确认）**：`fileHistoryCompleteSnapshot`（`fileHistory.ts:379-405`）在每轮结束时对**每个已跟踪文件无条件** `createBackup`（:393-396），**不检查内容是否变化**；`trackedFileBackups` 又逐轮**继承累积**（:307-316）⇒ 每轮 O(已跟踪文件数) 份全量拷贝，文件名带 `randomUUID()` 无法按名去重。

**方案**：
1. **内容不变则不新建**：镜像 `vN` 的 `checkOriginFileChanged` 把关（:276-288），内容未变则复用上一份 `completed`；
2. **同内容去重**：对内容做 sha256，相同则 `link()` 复用（**注意**：`assertSafeRegularFile` 拒 `nlink > 1`，已有 `severMigratedBackupLinks`（:899-942）会在首次读取时把 `nlink>1` 原子替换为私有副本——需与该机制协调，避免每次读取都触发复制）；
3. **版本上限**：每文件保留最近 K 个 `completed`。

⚠️ **不得破坏** `sessionRewindService.ts:1228-1229` 的 `frozen` 模式——它依赖 `-completed-*` 作为 turn 的 **after 边界**。

### F. 存量数据回收（3.0 GB transcript；⚠️ 须用户确认）

**方案**：一次性脚本改写 JSONL，把超阈 `originalFile` 替换为与 C 相同的「有界预览 + 引用」，保持行序与格式。

**硬性要求**：
- 先备份；
- 幂等 + 可续跑；
- 校验解析不变量保持（`parentUuid` 首键、行数不变、逐行 JSON 可解析）；
- 对已被 file-history 追踪的文件**无损**（原文可从备份取回）；
- ⚠️ **属数据修改，须用户明确确认后才执行**。

### G. 附加：传输与缓存（可选，收益明确）

- gzip 改**流式/异步**压缩（`zlib.createGzip` 或 `CompressionStream`），消除 `gzipSync` 的事件循环阻塞与整包内存放大。
- 客户端历史缓存（`CHAT_HISTORY_CACHE_BYTES=16MB`）当前**不保护活跃标签页**，大会话长期驻留内存；可评估对活跃会话也做窗口化。

### H. 读取预算收紧：`HISTORY_FULL_BYTES` 32 MB → **8 MB**（参数调参；本次仅入设计，未改代码）

**位置**：`src/server/services/boundedSessionHistory.ts:20`，生效点 `:175` `byteBudget = options.full ? HISTORY_FULL_BYTES : HISTORY_PAGE_BYTES`。

**语义**：`mode=full`（「一次读完」路径）**单请求输出字节上限**。超预算时不报 413，而是返回「最新的一片」并置 `historyComplete:false` + 给 `nextCursor`（客户端继续翻页）。

**收益**
- 单响应上限 32 MB → 8 MB：内存尖峰、远端同步 `gzipSync` 阻塞、单请求最坏耗时同步下降；
- 与 A/C 配合后（记录裁到 <48 KB），8 MB 可容 ~170 条 → 页数反而大降。

**三个必须知道的连带影响**
1. **不减少总字节，只重新分配**：客户端 `getFullHistory`（`desktop/src/api/sessions.ts:446`）在 `nextCursor` 非空时继续翻页，首屏之外的量改由 page 模式请求承担（本会话 33.2 MB → 首响应 ~8 MB + 约 6 次额外页请求）。
2. **单独改可能让页数变多**：真正的瓶颈是**超预算记录独占一页**（3.9 MB/条），降低预算并不缩小记录 → H **应与 A/C 同批落地**，不宜单独上。
3. **`historyComplete:false` 更频繁**：会触发 `historyWindowed` 横幅 + 更多 `recoverSessionHistory`（recovery lane cap=1）→ 形成新的排队来源。

**⚠️ 关键：真正的耗时上界不是它，而是扫描预算**
- `HISTORY_FULL_SCAN_BYTES` = **64 MB**（`:10`）才是单请求 I/O 硬上界。只把输出降到 8 MB、扫描仍留 64 MB，等于允许「读 64 MB 只吐 8 MB」——**延迟上界没变**。
- **建议配对**：同步把 `HISTORY_FULL_SCAN_BYTES` 降到 **24 MB**（= 输出 3× 余量）。依据：本会话记录 3.95 MB < `HISTORY_SEMANTIC_RECORD_BYTES`(8 MB) 阈值不会被跳过，故扫描量≈输出量；只有存在 >8 MB 被跳过记录时才需要更大余量。
- 扫描预算是否一并调**待裁决**。

**回归核对（已完成）**
- `boundedSessionHistory.test.ts` 的 full 用例断言为宽松区间（`entries.length > 0 && < 40`、`historyComplete:false`、最新片保留 `'39'`）→ 8 MB 下仍成立，**无需改测试**；
- 无 `.js` 孪生；全仓无硬编码 32 MB 断言（`HISTORY_FULL_SCAN_BYTES` 仅出现在 `toBeLessThanOrEqual` 断言中）。
- **生效方式**：server 侧 TS 由 bun 直跑，改后**仅需重启 sidecar**，无需 `vite build`（前端 bundle 不含该常量）。

## 八、风险与踩坑记录

1. **删字段 = 功能消失**：`originalFile` 是 schema 必填 `z.string()`（C1）+ UI 无保护 `.split`（C2）→ 必须保留**字符串**形态。
2. **不可整体删 `toolUseResult`**：被当「非人类消息」判别位（C3）。
3. **`bodyTruncated` 会翻转 `historyComplete`**（C9）→ 展示层裁剪必须与之解耦，否则触发 recovery 循环 + `historyWindowed` 横幅误显。**这是本方案最容易踩的坑。**
4. **recovery / 语义归约必须保留原文**：`sessionHistoryRecovery.ts:174` 的 workspace 证据、`teamService`、`workflowService` 依赖原始记录。
5. **顶层键序不可动**（C4）：新增键只能进 `toolUseResult` 内部。
6. **`HISTORY_SEMANTIC_RECORD_BYTES`=8 MB 是「整条跳过」而非截断**：只调小 `HISTORY_PAGE_BYTES` 属治标（反而页数更多）。
7. **并发写入**：翻页期间允许文件增长，但 `sourceVersion` 不匹配会**非重试**抛错（`api/sessions.ts:466`）——渐进渲染时需保证首屏已渲染再容忍后续失败。
8. **file-history 去重与 `nlink` 校验冲突**：硬链接去重会触发 `assertSafeRegularFile` 的 `nlink>1` 拒绝，需与 `severMigratedBackupLinks` 协调。
9. **远端鉴权**：新端点须过 `remoteBrowserPolicy` 同级约束。
10. **i18n 5 语言**：若新增 UI 文案（如「预览已截断，点击加载完整内容」）需覆盖 en/zh/jp/kr/zh-TW。
11. **`.js` 孪生**（C12）。
12. **v1 教训**：机制类结论必须以**日志/实测**坐实——本次白屏根因（120 s 超时）与 v1 推测（置空 `messages`）不同，靠诊断日志中 12 次 `timed out after 120s` 才纠正。

### ⚠️ 修正一：C 方案证伪

第六节 L1 / 第七节 C 的「裁掉 `originalFile` 并指向 file-history 备份」**不可行**。实测反证：

| 检查（本会话 20 个巨型条目） | 结果 |
|---|---|
| 内容互不相同 | 20 |
| 在 file-history 中找得到 | **5** |
| **找不到（裁掉即永久丢失）** | **15（75%）** |

原因：一轮内多次编辑**不逐次备份**，`trackedFileBackups` 只保轮次边界，且 `createBackup` 以 `sha256(path)@vN` 命名、并非内容寻址。故 C 若按原设计落地会**丢 75% 数据**。替代路径：A（传输层）+ E（存量去重）已覆盖主要收益；根治磁盘新增需「有界预览 + 自建内容寻址副本」（磁盘持平）或接受有损裁剪（需用户同意）。

### 修正二：gzip 阈值评估（用户提问）

**维持 `MIN_COMPRESS_BYTES = 128 KB`，不应改为按会话大小门控。** 裁剪后比率仍 **4.4–6.0x**（减的是量不是冗余）；压缩是**按响应**生效，按会话门控冗余且不准；成本已移出主线程，128 KB 档 2.4 ms 换 ~99 KB 下行（2 Mbps 链路约省 400 ms）。

附带发现：Bun `Response.json()` **不设 `content-length`**，`responseCompression.ts:66` 的快速跳过**从不触发**（小响应先被缓冲再判、并重建 Response）；开销微秒级，无需处理，但注释名不副实。
