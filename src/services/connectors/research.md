This report only verifies official documentation and source code; it did not log in to third parties, call business tools, or consume vendor quota. The following are official services that can be connected through the existing HTTP/SSE MCP client; this does not mean real end-to-end testing with every vendor account has been completed for this product. The final listing scope is determined by the catalog implementation.

## Authentication and vendor differences

- **The three map products** use developer keys, not automatic authorization from logging into a personal maps app. AMap and Baidu docs explicitly provide an HTTP endpoint; Tencent's `userGuide` raw HTML provides both `/mcp?key=<YourKey>&format=0` and `/sse?key=<YourKey>&format=0`. Browser scraping tools failed to parse the Tencent docs, so the raw official HTML was fetched over read-only HTTPS for verification. Using MCP doesn't bypass upstream WebServiceAPI quotas.
- **GitHub** officially states that remote MCP doesn't support Dynamic Client Registration. A generic OAuth button cannot reuse VS Code's client identity; doing OAuth would require us to register and manage a GitHub App/OAuth App. So this round chose PAT. The server supports a read-only header `X-MCP-Readonly: true`, or specifying toolsets. Sources: [host integration](https://github.com/github/github-mcp-server/blob/main/docs/host-integration.md), [configuration](https://github.com/github/github-mcp-server/blob/main/docs/server-configuration.md).
- **Notion** officially documents the Claude Code HTTP + `/mcp` OAuth flow. Don't treat a Notion integration secret as a static header option supported by the hosted MCP. Users can still only access content their own permissions allow.
- **Linear** officially supports OAuth 2.1 DCR, Bearer OAuth tokens, and API keys. New integrations use `/mcp`; `/sse` is a deprecated compatibility path. `/mcp/readonly` is optional. Multiple workspaces need separate auth contexts.
- **Supabase** hosted MCP uses DCR by default, so users don't need to create their own OAuth App; only specific clients without DCR support need a manual App. PAT is a viable alternative. Projects can be scoped via `project_ref`. Don't confuse this with self-hosted Supabase's internal MCP, which should not be exposed directly to the internet and uses a different authorization mechanism.
- **Canva** now recommends CIMD, but DCR is still kept for compatibility. The current client can use DCR, so it can be listed; don't misread "CIMD recommended" as requiring a pre-registered App. Each user must authorize separately; organization-level shared service accounts are not supported. Sources: [auth and setup](https://www.canva.dev/docs/mcp/), [manual registration and limits](https://www.canva.dev/docs/mcp/troubleshooting/).
- **Figma** officially documents the Claude Code `--transport http` + Authenticate flow, so there's no need to invent a PAT integration this round. It doesn't guarantee every account has all design write tools; real capabilities should be obtained from tools/list.
- **Hugging Face**'s canonical endpoint is `/mcp`, with the token as Bearer. For OAuth, the official example uses `https://huggingface.co/mcp?login`; bare `/mcp` can't be forced into OAuth. To reduce client registration differences, this round chose user tokens. [Official install example](https://github.com/huggingface/hf-mcp-server?ref=explainx), [Hub usage notes](https://huggingface.co/docs/hub/agents-mcp), [OAuth/CIMD](https://huggingface.co/docs/hub/oauth).
- **Context7**'s current official registry `server.json` declares the Authorization header as optional, supporting Bearer or a raw key. Older material often uses a `CONTEXT7_API_KEY` header; the catalog uses the current official configuration. Its dedicated OAuth endpoint is `/mcp/oauth`; the current recommendation is not to mix them.
- **Exa** officially documents an anonymous free tier and upgrading via `x-api-key`. Don't infer unlimited quota from a successful basic connection; failures should not automatically request a key or pay.
- **Stripe**'s official MCP is in public preview and supports OAuth and Bearer API keys. Being able to connect to financial data does not mean "user login authorizes all payments/refunds"; business write operations still follow the current tool execution authorization boundaries.

## Existing MCP boundaries in this repository

- The DTO at `src/server/api/mcp.ts:37` supports stdio/http/sse; from `:470` it parses remote URL/headers/oauth clientId/callbackPort; createServer at `:570` saves the config but only returns a snapshot, which doesn't mean it's authorized or usable.
- Routes at `src/server/api/mcp.ts:750` include GET list, GET `/:name/status`, POST create, PUT update, DELETE, and POST toggle/reconnect. **There is no generic HTTP `/authorize` API**, so new connectors cannot assume the existing API provides a complete OAuth loop.
- `performMCPOAuthFlow` at `src/services/mcp/auth.ts:847` is the reusable low-level OAuth flow; the remote bridge should call it explicitly and present authUrl/cancel, then reconnect and check tools/list.
- `addMcpConfig` at `src/services/mcp/config.ts:639` can save user-level connections; but if the new catalog stores credentials via sensitive plugin userConfig, it should keep plugin ownership and not write a second plaintext key.
- `serializeEditableConfig` at `src/server/api/mcp.ts:184` returns URL and headers. **Never return expanded secret query/header values as-is through this DTO.** New connectors' public state should only return the secret-free endpoint, a configured flag, and status; sensitive config is expanded at runtime as needed.
- `type: http` in the catalog corresponds to Streamable HTTP, not legacy SSE. No extra npx/mcp-remote is needed. This product's native client supports both transports; only use sse when the service is genuinely officially SSE-only.

## What acceptance means

Catalog entry exists ≠ configured ≠ OAuth complete ≠ tools/list succeeds ≠ business call succeeds. Protocol mocks can verify this app's install/auth state and call wiring, but cannot replace real end-to-end testing with vendor accounts. Test the protocol connection after the user clicks configure and provides an account/key; never auto-attempt login at startup, and never automatically call search, image, payment, or compute tasks to "check liveness".

### Fixed recipe deferred: Tushare

[Official doc 463](https://tushare.pro/document/1?doc_id=463) confirms that Tushare provides MCP, with users copying the configuration from MCP Server in their profile. But its text example writes `https://api.tushare.pro/mcp/token=<your Tushare token>`, while the WorkBuddy public catalog writes `/mcp/?token=...`; these differ in URL semantics. No request was made with a user Token, so we can't change the path to a query by inference and claim it's verified. We should wait for an explicit official configuration spec, or first provide a custom MCP configuration entry where users paste the address actually generated by the vendor console. Avoid shipping an unreliable fixed endpoint just for count.

Public WorkBuddy packages were used only as discovery leads; the vendors' generic client configurations are authoritative. Topic-specific services from the same vendor were not split into multiple brands to inflate the count.

Bazhuayu has a documentation discrepancy worth keeping: the [Claude tutorial](https://www.bazhuayu.com/docs/zh/mcp/integrations/claude) and ChatGPT tutorial recommend OAuth and list x-api-key as an alternative, while the generic client guide explicitly requires an API Key. A GET of the public OAuth metadata does return DCR, PKCE S256, and token auth `none`, but that only proves the discovery info exists and can't replace end-to-end testing with user authorization. This round chose `x-api-key`, which both docs explicitly support, and doesn't copy WorkBuddy's OAuth configuration as a generic promise.

Additional candidates not included in these 10: Tencent Lexiang's official repository `tencent-lexiang/lexiang-mcp-skill` requires two settings, a `company_from` query and a Bearer Token, which the current single-field adapter can't handle; Baidu Netdisk's official `baidu-netdisk/mcp` SSE service uses an `access_token` query, production integration requires an enterprise developer, and personal trials are time-limited. Lingxing's official guide has users copy a Server URL and X-Mcp-Key, and a generic fixed URL hasn't been confirmed; Jiandaoyun requires generating an authorization link in its console. The catalog was not filled out with private partner paths, default anonymous configurations, or guessed OAuth.
