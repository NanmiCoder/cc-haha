## BUG-001 | Built-in terminal is blank on first open under React StrictMode

- Severity: P0
- Status: fixed / verified
- Test cases: WIN-03, terminal basic smoke
- Scenario: open the built-in terminal tab at the top in a development build.
- Actual result: the terminal area is blank with no usable session; refreshing the settings page doesn't recover it.
- Expected result: the terminal creates only one runtime and shows `Running`, the shell, cwd, and an interactive prompt.
- Root cause: React StrictMode replays effects on first mount. The first cleanup immediately destroys the shared terminal runtime, and the second effect keeps holding the now-invalid object, so it can't restart.
- Fix: added a lifecycle version to the component effect; a genuine unmount still destroys the runtime in a microtask, while a stale cleanup from a StrictMode replay no longer destroys the current runtime.
- Changed files:
  - `desktop/src/pages/TerminalSettings.tsx`
  - `desktop/src/pages/TerminalSettings.test.tsx`
- Verification evidence:

## BUG-003 | Leftover pending confirmation after a permission mode control request is rejected

- Severity: P1
- Status: fixed / verified
- Test cases: DENY-01, DENY-02, permission mode switching
- How found: Windows `check:coverage` reliably failed to exit when running the three permission mode tests "confirm succeeds → CLI rejects → confirm times out" in sequence.
- Root cause: `ConversationService.setPermissionMode()` calls `requestControl()` after creating the confirmation Promise; when the CLI rejects the control request, the catch only clears the timer/callback without settling the confirmation Promise already created. Under coverage async tracking, that pending Promise drives subsequent timing tests into a sustained CPU state.
- Fix: keep the confirmation reject handle and introduce a settled guard and explicit `cancelConfirmation(reason)`; when the control request fails, clear the callback/timer, reject the confirmation, and rethrow the original CLI error unchanged. The confirmation timeout timer is only started after the control request succeeds, using the remaining total budget.
- Changed files:
  - `src/server/services/conversationService.ts`
  - `src/server/__tests__/conversations.test.ts`
- Verification evidence:
  - The three permission mode tests in sequence: 3 passed, 0 failed.
  - The same three cases under coverage: 3 passed, 0 failed, no longer hanging.
  - Full `conversations.test.ts` under coverage: all 96 named tests completed and passed; there was a separate `EBUSY` during Windows afterAll temp directory cleanup, which isn't a behavioral assertion failure.
  - The regression additionally asserts that after CLI rejection, `outputCallbacks` is empty and `pendingPermissionModeChanges` is empty.

## BUG-004 | Destroying a CONNECTING WebSocket under Bun leaves it stuck in CLOSING forever

- Severity: P1
- Status: fixed / verified
- Test case: WIN-05
- How found: after fixing BUG-003, the adapters stage of full coverage had 405 passed, 1 failed; `WsBridge > destroy cleans up all sessions without leaking connecting-socket errors` still had one error listener after 20ms.
- Root cause: Bun 1.3.11 replaces bare `ws` imports with a BunWebSocket compatibility layer. Calling `close()` or `terminate()` immediately on an unreachable connection still in CONNECTING leaves the socket stuck in CLOSING forever, never firing error/close again; the temporary error sink and close listener are therefore kept forever.
- Fix: in the CONNECTING state, no longer call the state-poisoning close/terminate. After removing business listeners, only attach teardown listeners: a natural error is consumed and cleaned up; if open happens first, then close normally and clean up on close/error. The original close path for OPEN/CLOSING/CLOSED is unchanged; production code adds no arbitrary timeouts.
- Changed files:
  - `adapters/common/ws-bridge.ts`
  - `adapters/common/__tests__/ws-bridge.test.ts`
- Verification evidence:
  - Focused tests: 13 passed, 0 failed.
  - Focused coverage: 13 passed, 0 failed; `ws-bridge.ts` lines 85.59%, functions 73.68%.
  - The regression waits conditionally for CLOSED and asserts open/error/close listeners are all 0.
  - `bun run check:adapters`: 406 passed, 0 failed.
  - Full `bun run check:coverage` after the fix: 5/5 suites passed.

## BUG-005 | Trace abort backstop timer spins a single core on Bun/Windows after being unref'd

- Severity: P1
- Status: fixed / verified
- Test cases: Trace/diagnostics stability, server quality gate
- How found: `check:server` hung on `trace-capture.test.ts`; when split out as a single file, it kept one CPU core fully busy before any test result output.
- Root cause: `captureResponseTraceSnapshot` uses a grace backstop timer for a permanently pending `reader.read()` that cancel can't wake, but that timer is immediately `unref()`'d. On Bun 1.3.11 Windows, when `Promise.race` is left with only the pending read and the unref'd timer, it busy-loops synchronously and the timer never fires.
- Fix: keep the backstop timer's event-loop reference, with a comment explaining it's the correctness backstop the function is currently waiting on and must not be unref'd.
- Changed file: `src/services/api/traceCapture.ts`
- Verification evidence:
  - The originally hanging case: 1/1 passed, 63ms.
  - Full `trace-capture.test.ts`: 61/61 passed, 281 assertions, Bun 2.67 seconds, exited naturally.
  - `bun run check:server`: 219 files, 2248 passed, 0 failed.
  - `bun run check:chat-contract`: 5 files, 299 passed, 0 failed.

## QA-003 | Reconciliation safety sweep test busy-loops waiting for an unref'd interval

- Severity: test infrastructure
- Status: fixed / verified
- Actual result: after the first 5 tests showed passed, the process stayed at one full core with no final summary; traced to the 6th, the low-frequency safety sweep case.
- Root cause: the Promise the test `await`s can only be resolved by a safety interval that production has already `unref()`'d; a pending Promise doesn't keep the event loop alive, so with no referenced timer the Bun runner busy-waits, and the test never reaches `watcher.stop()`.
- Fix: use the existing `waitFor` with a referenced `Bun.sleep` to wait for the first batch, and use `try/finally` to always release the blocked first batch and stop the watcher.
- Changed file: `src/server/services/localIndex/reconciliationWatcher.test.ts`
- Verification evidence: single case 1/1 passed, 191ms; full file 7/7 passed, 570ms, with a natural summary and exit.

## BUG-006 | On Windows, CONNECT connections make Electron tests time out when stopping the system proxy

## BUG-009 | Half-closed local connections pile up on Windows and take down the Session list

- Severity: P0 / Windows desktop core usability
- Status: fixed / focused + live Windows verified
- Triggering cases: WIN-06, CTX-01, session list and Scheduled smoke.
- Actual result: the left sidebar briefly showed `Session list failed to load` / `Request timed out after 120s`, which disappeared on its own after a later refresh. It wasn't only Sessions at the same time: at 16:59:19, Task list and turn-checkpoints timed out at 120 seconds simultaneously; at 17:04:01, `/api/sessions?limit=400` and `/api/scheduled-tasks` timed out at 120 seconds simultaneously, preceded by two 20-second context inspection timeouts.
- Windows on-site evidence: the Sidecar and CLI processes stayed alive throughout, with no Electron/Bun crash in the failure window; port 51529 had 9 leftover abnormal connection pairs, `FinWait2` on the Electron side and `CloseWait` on the Sidecar side. The Session directory had only 3 small JSONL files, and the local SQLite was also small, ruling out "scanning 400 Sessions is too slow".
- First-round root cause hypothesis: `ContextUsageIndicator`'s HTTP deadline and the server-side `get_context_usage` control budget were both 20,000 ms, so client abort and server timeout raced at the same moment, leaving localhost keep-alive sockets not wrapped up in time. This hypothesis only explained the early correlation and wasn't the final root cause.
- Final root cause: Electron/Chromium pools HTTP/1.1 local connections for a long time, while `Bun.serve` was configured with `idleTimeout: 60`. Chromium netlog proved that the failing source 4974 reused socket #1319 after it had been idle for about 104 seconds: the socket had sent and received normally many times before, and on reuse the client successfully wrote 684 bytes, but the server never returned response headers, and Chromium cancelled after 120,011 ms. On Windows, a socket that Bun has timed out isn't recognized by the client as closed, forming a stale keep-alive; any REST call reusing that connection — tasks, turn-checkpoints, workspace-status, etc. — is affected.
- Fix: kept the correct client/abort/health lifecycle fixes, and set the local `Bun.serve` HTTP `idleTimeout` to `0`, letting the Chromium client own the pooled connection lifecycle, so the server doesn't silently expire first while the client keeps reusing it. Adding `Connection: close` to all REST responses was tried, but 12 navigations produced 403 `TIME_WAIT`s, so that global strategy was reverted.
- Changed files:

  - `desktop/src/components/chat/ContextUsageIndicator.test.tsx`

- Verification evidence:

  - After rebuilding the Sidecar and restarting the same isolated Electron, real DeepSeek returned `WINDOWS_TIMEOUT_FIX_ACTIVE`, and the session list and context 2% were normal.
  - The fixed build's baseline was 0 `CloseWait` / 0 `FinWait2`; after Computer Use manually refreshed context 10 times in a row, still 0 / 0, with only normal `Established` and short-lived `TimeWait`.
  - Afterwards, a manual session list refresh took about 1.3 seconds and the Scheduled page opened in about 1.3 seconds, both without timeout; this only proved the short-duration scenario.
