## 6. P1 Windows / Electron stability

- [x] **WIN-01 | Automatic recovery after Renderer crash**: in a dedicated Windows test build, terminate only the Renderer child process. The main window should automatically reload once and become usable again, without a long white screen, main process exit, or repeated reloads; session tabs, settings, and history are restored from persisted state. The isolated config's `cc-haha/diagnostics/electron-host.log` should record process-gone, recovery-started, and recovery-loaded. — passed: after closing the pet window and confirming the isolated Electron had only one main Renderer (PID 40812), only that child process was terminated; within 3 seconds a new Renderer (PID 5696) started, and the Settings/Pets page, two session tabs, Huhu/192px, and the closed state were all restored and usable. The log recorded `process-gone`, `recovery-started`, and `recovery-loaded` in order.
- [ ] **WIN-02 | Brief and sustained unresponsiveness**: create a Renderer stall shorter than 10 seconds and then recover; the app should not reload by mistake. Then create sustained unresponsiveness longer than about 10 seconds; it should auto-recover only once. If it fails again, show the "Interface Recovery Failed" error dialog and leave a diagnostic record.
- [ ] **WIN-03 | Terminal and window destruction races**: with the built-in terminal continuously producing output, close the terminal tab, reload the Renderer, and close the main window once each; there must be no `Object has been destroyed`, main process crash, ghost output, or inability to reopen the terminal.
- [ ] **WIN-04 | System proxy/PAC instability**: enable a controlled system proxy or PAC, and while a chat request is being established, switch nodes, drop the CONNECT, and briefly disconnect and reconnect the network; the app must not show a main-process JavaScript exception, should be able to make requests again after the network recovers without restarting, and proxy auth failures must not silently fall back to DIRECT.
- [ ] **WIN-05 | IM WebSocket destroyed mid-handshake**: after starting an IM/H5 connection, while the WebSocket is still CONNECTING, switch sessions, reset, or exit the adapter; there must be no unhandled `error`, main process exit, or leftover connection, and after reconnecting the new session can send and receive normally.
- [x] **WIN-06 | Context timeouts must not take down local REST** — passed: Chromium netlog pinpointed the fault as reusing an HTTP/1.1 socket that had been idle for about 104 seconds but that Bun had already stopped handling per its 60-second `idleTimeout`; after writing `GET /api/tasks/lists/<session>`, it waited 120,011 ms for response headers, with turn-checkpoints/workspace-status timing out at the same time. After changing to `idleTimeout: 0`, rebuilding the real Windows sidecar, and merging task polling for the same session, the full MiniMax concurrent Task flow ran after the app had been idle for 85 seconds; the slowest task-list request was 235 ms and the slowest local API was 578 ms. After running for 137 seconds there were still 0 `CloseWait` / 0 `FinWait2` and no new timeouts. Then, with the sidecar compiled using the official Bun 1.3.14 Windows binary at the project's declared version, after being idle for 106 seconds, real MiniMax returned `IDLE0_BUN1314_OK`, and after running 131 seconds it was still 0 / 0 with no new timeouts; see BUG-009.
